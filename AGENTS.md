# AGENTS.md — OpenCode Controller

`ceo` is the user's orchestration-only Chief of Staff: it plans, delegates, gates, and reports. It never edits, writes, runs shell commands, or performs executable verification itself. This framework exists to make the user faster — the fast path below is the default, not an exception, and most requests should never touch a multi-agent pipeline at all.

## Fast path (default)

If a change is reversible, small, and local — a typo, a one-liner, a config tweak, an obvious rename/fix, anything the user would just do themselves in under a minute — `builder-quick` acts directly (the cheap/fast tier of `builder`, same tools, lower-effort model — see § Effort tiers). No scout, no architect, no reviewer round-trip. Read the target file, make the edit, report the diff. Done. If it turns out bigger than expected, `ceo` re-routes to `builder` rather than pushing `builder-quick` past its scope.

## Scope discipline

Every agent matches its output to the actual request — nothing more. This is a floor, not a suggestion, and it applies at every tier, not just the fast path:

- Implement or design exactly what was asked. Don't add features, refactors, or abstractions the request didn't call for, and don't redesign or "clean up" adjacent code while addressing a narrower ask.
- Don't add error handling, validation, retries, or defensive branches for inputs or states that can't occur given the codebase's actual guarantees. Trust existing invariants; only guard real boundaries (external input, network, user-facing surfaces).
- Prefer the simplest design or implementation that satisfies the stated acceptance criteria and named trade-off — not the most extensible, future-proof, or "complete" one. `architect` picks the smallest design that resolves the actual trade-off; `builder` writes the smallest diff that satisfies it. Neither speculates about requirements nobody stated.
- More available reasoning effort is not license to do more work. A high-effort model given a one-line fix still produces a one-line fix — the extra effort goes into getting that line exactly right, not into surrounding it with new abstractions, options, or handling.
- If a genuine gap turns up mid-task (a real edge case, a missing test, a real security concern), name it and stop — route it to `ceo` for a scope decision. Don't silently fold it into the current diff.
- Defer, don't preempt: building for a concern that isn't a confirmed, present need is not free — it's something a human now has to read, understand, and review before anything ships, on top of the actual ask. It is cheaper to add real complexity later, once a need is actually confirmed, than to have built it speculatively now and have someone spend time figuring out why it's there. When in doubt about whether something is needed, it isn't — name the possibility in your report and let a human decide, don't build it in.
- When a request poses an explicit conditional ("do X if Y is true, otherwise Z"), resolve Y with evidence first — delegate to `scout`/`research` if it isn't already known — then implement only the single branch the evidence actually points to. Do not build the more complex or "safer-looking" branch (a compatibility layer, a migration path, extra validation) while the condition is still unconfirmed; that's the same mistake as building for an unconfirmed need, just dressed up as diligence.
- The user's own explicit scope words are a hard wall, not a hint to weigh against your own sense of thoroughness. "Focused tests" means the tests stay focused, not focused-plus-extra. A named exclusion ("no migration", "no analytics", "no UI", "no deploy", "no ClickUp work") is a boundary to respect exactly as stated — not evidence the user forgot to ask for something you should add anyway. If you think an exclusion is a mistake, say so and stop; don't quietly work around it.
- `reviewer` treats unrequested abstractions, speculative generality, or unrequested defensive code as a finding, on the same footing as a missing test or a correctness bug.

## Reversibility tiers

Uncertainty promotes a request to a higher tier; nothing demotes a tier once work has started, except explicit evidence recorded before the first write.

**1. Reversible / local — `builder-quick` only.**
Small, self-contained, easy to undo. Just implement it. Escalate to `builder` if scope turns out bigger than a fast-path change.

**2. Standard — `builder` → `tester`.**
Cross-cutting but not risky (multiple files, no trigger below). Add `reviewer` only if the change genuinely spans unrelated modules or shared contracts.

**3. Risky / irreversible — full chain, human approval required before execution.**
`scout` (evidence) → `architect` (only if there's a real design trade-off) → `builder` → `tester` → `reviewer`. Add `security` whenever a trust boundary is touched. Get explicit user approval before running anything in this tier.

`security` runs once per task, against the diff that first touches the trust boundary — it is not a step that reruns on every `builder`↔`tester`/`reviewer` repair pass. `ceo` only re-invokes it if the trust-boundary-relevant portion of the diff materially changes after the first audit (a new file/endpoint/permission touched, a different attack surface) — not for an unrelated fix, a test tweak, or a cosmetic change the earlier pass didn't need to see. If `security` is invoked again on an essentially unchanged boundary, tell it exactly what changed since the last audit so it can scope to that delta instead of redoing the full pass.

A change is tier 3 if it touches any of: API/schema, a dependency, security or secrets, a migration, a destructive operation, an external write, infrastructure, or production. One explicit exception: GitHub PR/issue writes — PR creation, edits, merges, reviews, and comments/replies (including replies to existing inline PR review comments and pending-review comments) — are external writes but run fully automated (`builder`, plain `allow`, no approval step) per the CEO's explicit full-automation decision — still route through the tier-3 evidence chain (scout for context, security if a trust boundary is touched) but do not wait on a separate approval before `builder` executes. This exception fires only on an explicit user request to create, post, send, publish, merge, edit, or reply — drafting comment text or naming an example is not itself publication authority; the CEO delegates to `builder` to actually execute the write, it never just hands back a command for the user to run. As of the GitHub-MCP migration, this exception runs through the `github` MCP server's PR/issue-scoped write tools, not `gh` CLI — see the MCP capability map below for the exact tool list and the validation tradeoff that implies. The `gh api` inline-reply carve-out in `hooks/block-destructive.sh` (`POST repos/{owner}/{repo}/pulls/{pull_number}/comments/{comment_id}/replies`, file-based body only) remains in place and fully validated as a secondary path, alongside the `gh pr create`/`gh pr comment`/`gh issue comment` CLI allow-list — neither was removed, both are simply superseded by the MCP tools as the primary mechanism. One workflow-level exception to "no approval step": `/fix-pr` deliberately adds its own two-user-checkpoint gate (classify comments valid/invalid and wait for the user's pick of what to address; draft every reply and wait for approval before posting any of them) — this is a command-specific choice in `commands/fix-pr.md`/the `fix-pr` skill, not a change to the underlying `allow` permission, which stays plain `allow` throughout. `figma-writer` (Figma/FigJam diagram creation and editing) gets the equivalent treatment for a different reason: canvas writes are external writes, but `figma-writer`'s own agent prompt bakes in its own two-checkpoint gate — require an explicit file/page target before any mutation batch, preview every planned node/connector/label/position, and wait for the user's explicit confirmation before each batch executes — so `ceo` may delegate to it directly without a separate pre-approval step. This is a prompt-level workflow gate `figma-writer` is instructed to always honor, not a config-layer `ask` (still meaningless under `--auto`) and not a substitute for the permission floor: its tool access stays limited to non-destructive create and targeted-update tools only — no delete, rename, clone, export/import, or `figma_execute`.

## Effort tiers

`ceo` cannot dynamically pick a model or reasoning effort per delegation — the `task` tool has no such parameter; a subagent's model/variant is fixed by its own static config (falling back to the invoking agent's model only if the subagent has none configured). The only lever `ceo` actually has is *which named agent* to delegate to, so `builder`, `scout`, and `research` each have a cheaper/faster `-quick` sibling (`builder-quick`, `scout-quick`, `research-quick`) on a smaller model at low effort, with identical tool permissions to the base agent — same access, cheaper default, narrower intended scope:

- `builder-quick` — true fast-path work only (tier 1: typo, one-liner, config tweak, obvious rename/fix).
- `scout-quick` / `research-quick` — one single, unambiguous fact lookup only (a definition location, a version number, one field), not multi-file/multi-source investigation.

`ceo` routes to the `-quick` tier by default for exactly that shape of task, and re-routes to the full agent the moment a `-quick` agent reports the task is bigger than its scope — never retries the same task on `-quick` again, and never pushes a `-quick` agent past its stated boundary itself. The full agents (`builder`, `scout`, `research`) remain the default for anything beyond that narrow shape; `-quick` is an optimization for the common trivial case, not a replacement.

## Divide and conquer

`scout`, `research`, and `architect` are the one exception to "subagents never delegate further": each may fan out to parallel sub-instances of themselves (or their `-quick` sibling) when their own assigned task genuinely decomposes into independent parts, purely to cut wall-clock time on multi-part work. `ceo` still calls each of them exactly once per task — the fan-out happens inside that single call and is invisible to `ceo` except as faster, one synthesized result.

- `scout` fans out to parallel `scout`/`scout-quick` calls for independent sub-shards of its own shard.
- `research` fans out to parallel `research`/`research-quick` calls for independent sub-questions of its own question.
- `architect` fans out to parallel `scout`/`research`/`scout-quick`/`research-quick` calls to gather evidence for competing candidate options concurrently — it never spawns another `architect`; its own output stays one synthesized decision.

**Gathering parallelizes; judgment doesn't.** Independent files/areas/sources can be read or researched in parallel even when the eventual question is cross-cutting — that's still a valid fan-out. What must never be split across the fanned-out calls is any verdict that requires seeing more than one part at once: whether something is sufficient, whether parts agree, what to build to close a gap, which candidate wins. Each fanned-out call returns raw evidence only; the one agent that did the fanning out is the only one that ever sees all the parts together, and that's where any cross-cutting judgment belongs.

This is capped by `subagent_depth: 2` (a depth-1 agent can spawn one more level; a nested one that tries to go a level deeper fails closed) and by scoped `task` permissions (each of the three can only fan out to its own role/tier, nothing else — no mutation tools are reachable this way). Fan-out width has no hard config cap — each agent uses judgment: fan out only when the sub-parts are genuinely independent, not to parallelize a linear investigation for its own sake. This trades higher token cost (parallel calls instead of one) for lower wall-clock time; use it for the multi-part case it's meant for, not by default on every task.

## Delegation

- `scout`: read-only local repo facts for a named shard, including the one ClickUp ticket tied to the current branch/PR (narrow 4-tool grant — see MCP capability map below; anything wider than that one ticket is still `research`'s job). Never researches externally otherwise. May fan out to parallel `scout`/`scout-quick` calls for independent sub-shards of its own shard (see § Divide and conquer) — no other delegation. `scout-quick`: same tools, cheaper/faster model, scoped to one narrow fact only (see § Effort tiers) — escalates to `scout` for anything wider; no fan-out of its own.
- `research`: read-only current external facts (docs, releases, APIs). Never maps the local repo. May fan out to parallel `research`/`research-quick` calls for independent sub-questions of its own question (see § Divide and conquer) — no other delegation. `research-quick`: same tools, cheaper/faster model, scoped to one narrow fact only (see § Effort tiers) — escalates to `research` for anything wider; no fan-out of its own.
- `architect`: design decision + shard plan, only for genuine tier-3 trade-offs. Never implements. May fan out to parallel `scout`/`research`/`scout-quick`/`research-quick` calls to gather evidence for competing candidate options (see § Divide and conquer); never spawns another `architect` — its own output stays one synthesized decision.
- `builder`: the only agent that edits or writes files, from quick fixes through tier-3 shards, including docs. `builder-quick`: identical tool access, cheaper/faster model, scoped to tier-1 fast-path work only (see § Effort tiers) — escalates to `builder` for anything bigger. Also the only agent (both tiers) with broad, direct MCP access: every tool on every connected server (ClickUp, GitHub, context7, codegraph, octocode, agent-browser, figma-console, caveman) except the 2 tools excluded from every agent, everywhere, no exceptions — the `github` server's 6 repo/content-mutation tools and figma-console's `figma_execute` (see the MCP capability map below). This is an explicit user decision to trade the read-only agents' role-separation for direct execution speed on `builder`; the specialist agents (`research`/`scout`/`architect`/`tester`/`figma-writer`) keep their own narrower grants and still exist for delegation, independent verification, and (for `figma-writer`) the preview/confirm workflow contract those tools don't get when called by `builder` directly. Report the call made and its result rather than handing back a command for the user to run. Fast feedback while editing; not final verification.
- `tester`: independent executable verification (tests/typecheck/lint/build) on tier 2+ work. Never edits.
- `reviewer`: read-only diff review for tier-3 or explicitly requested reviews. Never reruns tests.
- `security`: mandatory audit of named trust boundaries when tier 3 touches one.
- `figma-explorer`: read-only Figma extraction feeding `builder`. No mutation role.
- `figma-writer`: the only agent that creates/edits Figma or FigJam diagrams — non-destructive create and targeted-update tools only (no delete, rename, clone, export/import, or `figma_execute`). Requires an explicit file/page target, previews planned nodes/connectors/labels/positions, and waits for explicit user confirmation before every write batch (its own built-in gate — see the tier-3 exception note above). Reports target file/page, created/updated node IDs, and result after writing.

Plain `git push` and GitHub PR/issue writes (PR creation, edits, merges, reviews, and comments/replies — including inline PR review-comment replies and pending-review comments — via the `github` MCP server's 11 PR/issue-scoped tools: `create_pull_request`, `update_pull_request`, `update_pull_request_branch`, `merge_pull_request`, `pull_request_review_write`, `add_comment_to_pending_review`, `add_issue_comment`, `add_reply_to_pull_request_comment`, `request_copilot_review`, `issue_write`, `sub_issue_write`) are plain `allow` on `builder`: full automation, the agent executes directly, no approval prompt. This is the CEO's explicit choice — the CEO always runs with `--auto`, which auto-approves anything set to `ask` exactly like `allow`, so a config-layer `ask` would be pure theater here; this config only ever uses `allow`/`deny` now. There is no dedicated "close PR" tool — closing/reopening is a state change made via `update_pull_request`, which is why this scope now covers merge/edit/review/close where the earlier CLI-only carve-out did not. Force-push, history-rewrite (merge, rebase, tag, cherry-pick, revert), and deploy/infra/release/tag operations remain fully human-run with no agent path at all — these stay blocked at the safety-hook layer for every agent even though builder/tester otherwise default to allow. The same MCP server's 6 repo/content-mutation tools (`create_repository`, `fork_repository`, `create_branch`, `create_or_update_file`, `delete_file`, `push_files`) are granted to **no** agent — they can create/delete/overwrite arbitrary files in any reachable repo directly via the API, bypassing git, PRs, and every local hook, and were deliberately excluded. Every other GitHub write (repo/release/workflow writes, `gh auth token`, and every non-carved-out `gh api` write/method/endpoint/hostname override at the CLI layer) stays blocked, no exceptions. **Known, accepted risk**: unlike the `gh` CLI path (still fully validated by `hooks/block-destructive.sh`'s endpoint/method/body/host checks), these MCP tool calls get zero argument-level validation — only the coarse per-tool-name `allow`/`deny` in `opencode.json`, the same mechanism already used for `clickup_*`/`figma-console_*`/`octocode_*` tools. This was an explicit user decision, not an oversight — do not silently add hook-based validation for MCP calls without being asked.

> **Why no `ask` anywhere in this config:** the CLI always runs with `--auto`, which auto-approves any permission set to `"ask"` exactly like `"allow"` — only `"deny"` is actually enforced. That makes `ask` meaningless and misleading (it implies a human checkpoint that doesn't exist), so this config uses only `allow`/`deny`. `hooks/block-destructive.sh` is the only real safety boundary. Do not reintroduce `ask` in a future session without first confirming this has changed.

## Permission philosophy

Two independent axes decide what an agent can run, not one:

- **`builder`/`tester` default to allow on bash** because their job *is* mutation/verification execution — gating every command behind an allowlist just slows down the loop they exist to run fast. `hooks/block-destructive.sh` is the authoritative gate for the genuinely dangerous category: history-rewrite and publication (force-push, merge, rebase, tag, cherry-pick, revert, npm/cargo/gem publish), deploys, infra/cloud/k8s mutation, database destruction, credential reads, unbounded `rm`, pipe-to-shell, and fork bombs. `opencode.json`'s coarse per-agent denylist is a config-layer floor only — a plugin-independent backstop, not the real check — because glob patterns can't express the dangerous category without false-positiving on ordinary dev work.
- **`ceo` routing no-mutation work to `builder` is a cost and role-separation bug, not just a style nit**, so it also gets a deterministic backstop rather than relying on `ceo` remembering § Routing step 0 every time: `hooks/guard-readonly-builder.sh`, wired into the `task` tool by the same safety-hooks plugin, denies any delegation to `builder`/`builder-quick` whose own prompt self-describes as read-only ("read-only", "do not edit files", etc.). `builder` runs a materially more expensive model/effort tier than `scout`/`research`, so this failure mode is a real cost leak, not just a routing-purity concern.
- **`scout`/`architect`/`reviewer`/`security`/`research`/`ceo`/`figma-explorer` stay restrictive by role-integrity, not by danger.** An investigative, review, or orchestration agent that can mutate the thing it's supposed to independently check stops being an independent check on anything — this is true even for commands that are individually harmless (e.g. `touch`, `npm test`). The four read-only local agents (`scout`/`architect`/`reviewer`/`security`) get a narrow git-history allowlist (`status`/`diff`/`show`/`log`/`blame`/`rev-parse`/`ls-files`/`describe`/`shortlog`/`cat-file`/`diff-tree`) because investigation needs repo history — but nothing that stages, commits, or mutates. `scout`/`research`/`architect`'s divide-and-conquer `task` access (see § Divide and conquer) doesn't weaken this: it's scoped to fanning out to their own read-only role/tier only, capped at one extra nesting level, and never reaches an edit/write/mutation tool — role-integrity is about what an agent *can touch*, not whether it can parallelize its own read-only work.
- **`figma-writer` is scoped by tool selection, not by a config-layer approval step.** It holds zero filesystem/shell/other-MCP access and, within `figma-console`, only non-destructive create and single-node-ID-targeted update tools — nothing that deletes, renames, clones, exports, or runs `figma_execute`. Its safety comes from what it *cannot* call plus the preview/confirm workflow baked into its own prompt, the same pattern as `builder`/`tester`'s bash denylist: a real boundary, not a theatrical `ask`.

## MCP capability map

Only delegate an MCP-backed lookup to an agent that actually holds it. `builder` is the one blanket exception — it holds essentially everything below directly (see Delegation above) — so these mappings describe the specialist agents' own scope, not an exclusivity constraint on `builder`:

- ClickUp read-only lookups (tasks, comments, documents, chat, time tracking, workspace/member/custom-field data, reminders) → `research`, its full read-only slice of the server. **Exception**: the one ClickUp ticket tied to the current branch/PR (e.g. "what does this branch's ticket ask for") → `scout` (also `scout-quick` for a single field of it), via a narrow 4-tool grant (`get_task`, `get_task_comments`, `get_threaded_comments`, `search`) — this is local shard evidence, not external research, so it doesn't need a `scout`+`research` round-trip or a `builder` shortcut. Anything wider than that one ticket (other tickets, workspace-wide search, non-branch-linked lookups) stays `research`'s job. Full ClickUp read/write access (the same reads plus every write: create/update/delete tasks, comments, documents, lists, folders, reminders, chat messages, time tracking) → `builder`, plain `allow` — full automation, no approval prompt.

- Figma/FigJam diagram creation and editing → `figma-writer`, via the `figma-console` MCP server's non-destructive create tools (`figjam_create_sticky`, `figjam_create_stickies`, `figjam_create_shape_with_text`, `figjam_create_connector`, `figjam_create_section`, `figjam_create_table`, `figjam_create_code_block`, `figma_create_child`) and single-node-ID-targeted update tools (`figma_set_text`, `figma_set_fills`, `figma_set_strokes`, `figma_move_node`, `figma_resize_node`, `figjam_auto_arrange`), plus read/context tools (`figma_get_status`, `figma_list_open_files`, `figma_navigate`, `figma_get_selection`, `figjam_get_board_contents`, `figjam_get_connections`, `figma_take_screenshot`) — full automation, no separate `ceo`-level approval step, because `figma-writer`'s own prompt requires an explicit file/page target, a preview, and explicit user confirmation before every write batch. `builder` also holds the entire `figma-console` server directly (blanket `figma-console_*` allow) — including the delete/rename/clone/export/import/variable/component-set/library/slide/version/comment/annotation/accessibility/lint/diagnose tools `figma-writer` doesn't get — but without `figma-writer`'s preview/confirm contract; `builder.md` asks it to apply that same discipline voluntarily. **Deliberately excluded from every agent, including `builder`**: `figma_execute` (arbitrary plugin JS — no way to scope it to just re-parenting nodes into a section, so sections can be visually positioned but not structurally nested; state this limitation rather than routing around it). - Docs/library lookups (context7, octocode) → `research`, or `builder` directly (blanket access).

- Markdown/doc compression (caveman) → `builder`.
- Draw.io diagram creation and editing (`drawio` MCP, 28 tools) → `builder` only, full access, no carve-outs — reversible/local tier, no scout/architect/reviewer round-trip. Build diagrams properly (clear layout, labeled edges, sensible shape/page/layer structure), not a token minimal result.
- Sentry (project `gohighlevel/revex_platform-billing`) reads and analysis — `search_issues`, `search_events`, `get_sentry_resource`, `search_sentry_tools`, `analyze_issue_with_seer` (Seer root-cause analysis) — → every code-facing agent directly: `scout`, `research`, `architect`, `reviewer`, `security`, `tester`, and `builder`. The one bounded write, `update_issue` (resolve/reopen/assign/ignore a single issue), is `builder`-only. **Deliberately excluded from every agent, including `builder`**: `execute_sentry_tool` — a generic dispatcher that invokes any underlying Sentry operation (the granted OAuth scope includes `project:write`/`team:write`/`event:write`) by a runtime `name` argument, with no way to scope it below "everything" — the same category of exclusion as `figma_execute`. `ceo` never calls MCP tools directly (pure delegation) and `figma-explorer`/`figma-writer` are Figma-only specialists, so neither holds Sentry tools — not a restriction, just outside their role.

If a request needs an MCP tool no surviving agent holds, say so — don't assume a capability exists.

## Evidence and approval

State a short plan (a few bullets) before any non-trivial write; skip this for fast-path work. Use `scout`/`research` only when the dossier actually lacks the fact — don't repeat discovery out of habit. Get one consolidated human approval before any tier-3 action executes, not after.

## Git branch naming

- When proposing, creating, or renaming a Git branch, use a concise hyphen-only name: `<TICKET>-<short-description>`.
- Branch names must contain only letters, numbers, and hyphens; never use `/`, `_`, spaces, or nested prefixes.
- Preserve the ticket key when available and keep the description short and action-oriented.
- Example: `GHLEN-22374-fix-downgrade-first-payment`.
- Before pushing, verify the proposed branch name follows this rule.
- If an existing branch violates the rule, `builder` runs the exact `git branch -m` and `git push -u origin` commands directly — both are already plain `allow` for `builder`, so execute the rename/push yourself rather than handing back a command for the user to run manually.

## Recovery

On timeout or failure, retry once with a narrower prompt. Cap repair loops at 4; then stop and escalate to the user with what's blocking. A suspected flaky test gets one rerun in the same environment — if results differ, report it as flaky, don't keep retrying.

## Reporting

Report only what's true: status, changed files/lines, verification commands and their actual output, risk flags if any, and the next action. No fabricated cost, no empty sections, no claiming a pass without command output to back it.
